# QQ 群治理与 OneBot 接入草案

> 本文是未实现功能的设计草案，不描述当前 AmiyaEden 行为。功能落地后，必须将当前事实迁入对应的 `architecture`、`api` 和 `features/current` 文档。

## 背景

AmiyaEden 已经是军团成员身份、主人物、主军团和系统职权的权威来源。QQ 群治理应直接使用这些本地数据处理入群申请、成员名片同步和审查留痕，而不是依赖独立机器人服务再次查询 AmiyaEden。

NapCat 只负责连接 QQ 并实现 OneBot V11 协议；它不保存群规则、不判断成员资格、不承担任务重试或审计。AmiyaEden 负责所有业务决策、持久状态、周期维护和管理界面。

## 当前基础与限制

- `User` 已保存 QQ 号和主人物 ID；人物、军团和职权可通过现有用户、人物和职权服务组合得到。
- 后端已具备 PostgreSQL、Redis、cron、共享后台任务管理器、任务执行历史和系统审计能力。
- 现有 OneBot Webhook 只支持经 HTTP 向固定群或私聊发送通知；它不接收 OneBot 事件，也不处理入群审批或群名片动作，不能作为本功能的协议层复用。
- 当前 cron 注册表和锁只解决进程内周期任务去重，不是每个 QQ 事件都可依赖的持久任务队列。

## 目标与非目标

### 目标

1. 接收一个 NapCat 机器人账号的 OneBot V11 事件。
2. 按每群规则，使用本地 QQ、主人物、军团和职权数据判断入群申请、成员名片目标态和在群成员资格。
3. 将 QQ 写操作放入可恢复的 PostgreSQL 持久任务队列，并完整记录审查和动作结果。
4. 按群定期扫描当前成员；对连续确认不符合规则的成员自动创建清退任务。
5. 在 Seat 的系统管理中管理群规则、扫描策略、运行态和处理失败任务。

### 非目标

- 不兼容、迁移或调用任何 Python QQ Bot。
- 不实现多机器人账号。
- 不实现多实例 OneBot 连接选主；首期部署保持单个 Seat 后端实例。
- 不向外部系统提供 QQ 群治理运行态或群规则 API。

## 提案

### 运行架构

NapCat 作为反向 WebSocket 客户端，连接 AmiyaEden 暴露的内部路径 `/internal/onebot/v11/ws`。连接握手必须校验 OneBot Token，并校验连接上报的 `self_id` 与 Seat 私有配置中的唯一机器人 QQ 一致。该路径仅允许受控内网访问，不通过公网反向代理暴露。

OneBot 接入层只负责连接、事件解析、Action `echo` 对应和协议错误处理。业务规则必须位于 `service`；数据库读写必须位于 `repository`；HTTP/WebSocket handler 不得直接决定批准、拒绝或改名片。

```text
NapCat 事件
-> OneBot 连接管理器
-> 群治理服务
-> 本地用户 / 人物 / 职权查询 + 群规则
-> PostgreSQL：运行态、审查和动作任务
-> 动作 worker
-> OneBot Action
-> NapCat / QQ
```

### 身份与准入判断

群治理服务直接复用 Seat 的本地用户、人物、职权和实体名称能力，不通过 `/api/v1/external/*` 查询自身。

- 同时配置允许军团和允许职权时，用户必须同时满足两项。
- 仅配置一项时，只检查该项。
- 两项都为空时，不自动放行。
- QQ 未绑定用户、主人物缺失、军团信息缺失或内部查询异常，统一进入 `REVIEW_WAIT`。
- 不匹配的入群申请默认 `REVIEW_WAIT`；只有群规则显式选择 `auto_reject_unmatched` 时才生成拒绝动作。
- 已入群成员在事件触发时只同步名片或标记待复查；周期扫描负责确认持续不合规的成员并触发自动清退。

每群规则新增成员违规策略：`review_only` 或 `auto_kick_after_confirmed_mismatch`。前者为默认值；后者在同一成员连续两次周期扫描得到明确不匹配结果、且从第一次明确不匹配起已观察至少 2 小时后，自动创建清退任务。群规则可在安全范围内配置 2~3 次确认和 1~6 小时观察期。

用户未绑定 QQ、主人物或军团资料缺失、内部查询异常和 OneBot 查询失败均是 `UNKNOWN`。`UNKNOWN` 不审批、不清退、不累计不合规次数，并中断该成员的连续确认链；系统在 5 分钟加随机抖动后安排复查。一次有效匹配也会清零不合规连续次数。连续三次 `UNKNOWN` 必须创建管理员通知，但仍不得触发自动写操作。

名片模板仅允许使用 `nickname`、`primary_character_name` 和 `primary_corporation_name`。模板在保存规则时校验；渲染结果为空或超出 QQ 平台限制时不创建名片动作，并写入可见审查原因。

### 领域数据

新增 GORM 模型并纳入 Seat 的 `AutoMigrate` 与必要的自定义索引：

| 模型 / 表 | 责任 |
| --- | --- |
| `QQGroupGovernancePolicy` | 每群启用状态、军团/职权白名单、拒绝策略、成员违规策略、扫描间隔、连续不合规阈值、名片模板和修改审计关联信息 |
| `QQGovernanceEvent` | 标准化 OneBot 事件、事件唯一键和最小必要 payload 摘要 |
| `QQGroupMemberState` | 群号与 QQ 的当前生命周期、目标名片、Seat 用户 ID、版本、最后检查时间和连续明确不合规次数 |
| `QQGovernanceReview` | 每次决策、原因、Seat 最小快照、来源和创建时间 |
| `QQGovernanceActionTask` | 扫描、审批、名片和清退动作的类型、幂等键、目标版本、payload、状态、重试、租约和执行时间 |
| `QQGovernanceActionLog` | 每次 OneBot 动作尝试的脱敏请求摘要、结果、错误和关联任务 |
| `QQGovernanceReconcileCursor` | 每群巡检游标、分片进度、最后完成时间和下次扫描时间，保证重启后可继续扫描 |
| `QQGovernanceRiskControlState` | OneBot 动作失败窗口、当前熔断级别、半开探测和恢复时间 |

Seat 用户资料仍是权威数据。审查快照只能保留用户 ID、昵称、主角色、主军团和职权编码，禁止保存 ESI Token、QQ 原始消息、登录 IP 或 OneBot Token。

### 事件、状态与动作生命周期

首期接收下列 OneBot 事件：

- `request/group/add`：入群申请；
- `notice/group_increase`：成员已加入；
- `notice/group_decrease`：成员离开。

每个事件先以平台事件字段组合出的唯一键落库去重。事件、成员状态更新、审查记录和后续动作任务必须在同一数据库事务内提交；重复事件不得重复创建动作。

成员运行态为 `JOIN_PENDING`、`IN_GROUP_VALID`、`IN_GROUP_REVIEW`、`IN_GROUP_INVALID_CANDIDATE`、`IN_GROUP_INVALID_CONFIRMED` 或 `LEFT`。首次明确不合规只进入候选态；满足连续次数和观察期后才进入确认态并允许生成清退任务。每次状态改变递增版本；动作 worker 执行前必须确认任务版本仍与当前成员状态一致，过期任务标记取消。

首期 OneBot 动作只有：

- `get_group_member_list`：读取当前群成员，供周期扫描使用；
- `set_group_add_request`：批准或拒绝入群；
- `set_group_card`：同步群名片。
- `set_group_kick`：清退连续确认不符合规则的成员；
- `notify_admin`：对重复 `UNKNOWN`、死信和熔断状态发送 Seat 管理端通知。

任务状态为 `pending`、`scheduled`、`running`、`retry_wait`、`succeeded`、`cancelled` 或 `dead`。任务语义为至少一次。任务记录必须包含租约 Token、领取时间和过期时间；worker 崩溃后可重新领取过期任务。名片更新按目标值天然幂等；入群申请遇到平台返回“已处理”等确定终态时视为成功。清退动作必须在执行前再次核对成员状态版本、不合规连续次数、观察期和群规则仍启用，避免旧扫描结果清退已恢复资格的成员。超过重试上限的任务进入 `dead`，仅允许超级管理员显式重试。

### 任务去重、合并与优先级

任务中心必须以群号、QQ 和动作建立稳定幂等键：`approve:{group}:{qq}`、`reject:{group}:{qq}`、`card:{group}:{qq}`、`kick:{group}:{qq}`。同一申请只保留一个审批或拒绝任务；名片任务只保留同一成员最新目标态；存在有效清退任务时，取消未执行的审批和名片任务，且相同目标版本不得重复创建清退任务。

优先级数值越小越先执行：审批/拒绝为 10，首次名片同步为 30，巡检名片修正为 60，清退为 90，管理员通知和低优先级修正为 100。动作 worker 必须先按优先级、再按 `run_after` 和创建时间领取任务。

### 周期任务与运维

新增群治理周期扫描与维护任务，由现有 cron 注册与任务管理体系触发。cron 每 15 分钟创建一次巡检批次；每批最多处理 50 名成员，并通过持久游标均匀推进，不得简单地每 30 分钟全量扫描所有群。成员少于 100 人的群可在 1 小时内完成一轮；100~500 人的群使用滚动批次；500 人以上的群必须分片，使全量扫描在 2~6 小时内完成。

扫描任务读取群成员列表，批量读取本地用户、人物和职权资料，分批重算成员资格、同步有效成员名片，并为达到自动清退阈值的成员创建 `set_group_kick` 任务。扫描必须跳过机器人自身，且对同一群、同一成员遵守动作限流。若 OneBot 成员列表接口不提供分页，系统仍必须按稳定 QQ 排序和持久游标分批处理，不能在一次 cron 运行中集中处理全群。

维护任务用于：

- 回收租约过期的动作任务；
- 将超过重试上限的任务标记为死信；
- 清理超过保留期的治理事件、审查和动作日志。

延迟复查、下次群扫描和动作重试均通过持久任务的 `run_after` 调度，不以进程内 timer 保存业务状态。`review_only` 群只记录扫描发现的问题；启用自动清退策略的群不需要额外人工确认，但每次清退前后必须写审查和动作审计。

### 限流、抖动、重试与熔断

所有 QQ 写操作必须经过统一 worker 和 Redis 分布式限流器：全局平均 1 次/3 秒、突发容量最多 3；普通群级动作至少间隔 8 秒；清退动作在同一群至少间隔 30 秒；同一 QQ 的任意管理动作至少间隔 60 秒。初始动作延迟与抖动为：审批/拒绝 2 秒加 0~4 秒、名片同步 15 秒加 0~45 秒、清退 60 秒加 0~180 秒。自动名片同步对同一成员 24 小时内最多执行 2 次。

可重试错误包括网络超时、临时连接失败、OneBot 服务端错误和平台繁忙；权限不足、参数非法、群不存在、成员已离群和名片内容非法为不可重试错误。可重试任务采用指数退避加抖动，依次为 30~60 秒、2~5 分钟、10~20 分钟、30~60 分钟，第 5 次失败进入 `dead`。

风险控制以最近 5 分钟 OneBot 动作结果计算：失败率超过 20% 时进入一级降级，名片和巡检速率减半但审批继续；失败率超过 40% 或出现疑似平台风控错误时进入二级熔断，暂停清退和批量名片修正，仅处理本地资料明确有效的审批；出现大量动作拒绝时进入三级熔断，暂停所有自动写操作 30 分钟，继续记录事件并通知管理员。熔断期满后以少量任务半开探测，成功后逐级恢复；超级管理员可查看并手动解除熔断。

### 可观测性

运行时必须输出结构化日志，至少包含任务 ID、任务类型、群号、QQ、目标状态版本、任务状态、失败原因和重试次数。管理面和监控指标至少提供：每分钟任务创建/成功/失败数、审批与名片同步延迟 P50/P95、清退执行数、OneBot Action 成功率与超时率、熔断次数、各群动作分布、扫描游标滞后和死信任务数量。日志和指标不得包含 OneBot Token、ESI 凭据或完整原始事件内容。

### 管理面与权限

在“系统管理 → QQ 群治理”新增管理面，首期全部由 `super_admin` 管理：

- 配置和启停单群治理规则；
- 配置成员违规策略、扫描间隔和自动清退阈值；
- 查询群规则、成员运行态、审查历史、动作记录和死信任务；
- 查看最近扫描结果、明确不合规次数和已创建的清退任务；
- 对死信任务发起人工重试；
- 手动批准、拒绝、同步名片、清退指定成员或立即巡检指定群；
- 查询成员本地绑定判断结果，并查看或解除当前 OneBot 熔断状态；
- 查看 OneBot 当前连接状态，但不展示 Token 或原始事件 payload。

拟新增的 Seat API 位于 `/api/v1/system/qq-governance/*`，使用现有 JWT、系统管理能力和 `super_admin` 门禁。WebSocket 接入路径不属于管理 API，也不接受 Seat JWT。

## 安全与可靠性不变量

- OneBot Token 仅来自私有配置，不写入响应、审计、日志或任务 payload。
- 未鉴权、机器人 QQ 不匹配或来自非受控网络的 WebSocket 连接必须拒绝。
- Seat 关停时停止接收新任务，并让已领取任务通过租约恢复；不得留下只存在于内存中的待执行动作。
- QQ 平台不可用、Action 超时或协议异常时，只能重试或进入死信，不得把未知结果当作批准、拒绝或已同步。
- 不得把通用 Webhook 的任意 URL 配置作为群治理 OneBot 连接配置。
- 原始 OneBot payload 只保留完成去重、重试和审计所需字段；其余内容不得入库，必要字段必须脱敏或加密保存。

## 验证与验收

- 策略单测覆盖军团/职权组合、空规则、未匹配、资料不完整、待复查、连续不合规计数、观察期、有效匹配与 `UNKNOWN` 清零、自动清退和名片模板。
- OneBot 合约测试覆盖反向 WebSocket 鉴权、唯一机器人识别、三类事件解析、成员列表读取、`set_group_kick`、Action `echo` 匹配和协议错误。
- 持久任务测试覆盖事件去重、任务合并和优先级、目标版本取消、租约回收、退避、死信、重复执行容忍，以及旧扫描任务不得清退已恢复资格的成员。
- 服务集成测试覆盖 QQ 号到 Seat 本地用户/主人物/职权查询、审查、群成员扫描、动作入队、自动清退和审计闭环。
- 管理面测试覆盖 `super_admin` 权限、脱敏输出和失败任务重试。
- 限流与熔断测试覆盖全局/群/动作/用户窗口、随机抖动、三级熔断、半开恢复和 `UNKNOWN` 管理员通知。
- 稳态压测覆盖短时间 50 个申请、100~500 人巡检、30% 查询异常和偶发 OneBot 动作失败，验证不会爆发式调用、能自然退避并最终恢复一致状态。
- 落地时执行仓库规定的 `go test ./...`、`golangci-lint run ./...` 和 `go build ./...`。

## 建议实施阶段

1. 最小闭环：OneBot 连接、事件入库、本地资格判断、审批/拒绝、延迟名片同步、持久任务、执行日志和全局/群/动作级限流。
2. 可靠性：租约恢复、指数退避、`UNKNOWN` 延迟复查与管理员通知、扫描游标、分片巡检和死信任务重试。
3. 治理：自动清退、观察期、熔断器、完整管理面、指标和手动补偿。
4. 规模化：独立 worker、多机器人账号、多实例连接选主和更细粒度的风险控制。

原 PRD 中面向独立机器人服务的外部成员资料接口、缓存、负缓存、singleflight 和该接口熔断，不直接迁入本草案：Seat 对自身用户、人物和职权执行本地服务/数据库查询。OneBot 平台调用仍保留限流、重试、熔断和审计要求。

## 开放问题

- 生产 NapCat 的固定版本、容器镜像和 OneBot V11 配置文件由部署方案确认。
- 入群申请 `flag` 的有效窗口和“已处理”响应码需要在目标 NapCat 版本上做集成验证后固化为重试分类。
- 审查日志、动作日志和事件日志的保留期由运维策略确定。

## 实施状态

截至 2026-07-11，首期最小闭环已在 AmiyaEden 落地：独立 OneBot V11 反向 WebSocket 接入、专用令牌/机器人 QQ/受控网段校验、群规则持久模型、事件去重、本地 QQ/主人物/军团/职权准入判断、审批/拒绝/名片持久动作任务、租约恢复、重试、死信和 Redis 限流均已启用。当前实现说明见 `docs/features/current/qq-group-governance.md`。

周期成员扫描、自动清退、熔断器、完整管理页面和接口、多机器人、多实例连接选主、Python Bot 兼容和对外群治理 API 仍未实现，继续属于本草案的后续阶段。
